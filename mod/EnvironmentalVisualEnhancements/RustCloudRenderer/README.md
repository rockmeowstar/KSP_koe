# Rust cloud shader compiler

The current target is software half-to-float unpacking in `Scatterer-EVE/RaymarchCloud`. Rust analyzes the instruction graph and emits a Direct3D shader using native GPU half conversion. It does not change textures, ray steps, precision, lighting or the EVE renderer's resource bindings.

The frontend checks container/chunk bounds, rejects overlapping chunks and handles explicit-length custom-data blocks. The inspector requires byte identity when reconstructing the original instruction stream. Static instruction counts are not executed-work counts or FPS predictions.

The compiler tracks individual register components, computes conservative bit dependencies and recognizes expressions depending on one packed half value. Each distinct expression must agree with the integer IEEE conversion for all 65,536 inputs. Proven expression graphs are reused across shader compilations with full structural equality. Native conversion canonicalizes NaNs on the tested GPU, so an integer repair preserves their original signs and payloads. Control-flow liveness removes dead calculations; empty branches and their unused conditions are then removed together. Interference-graph register reuse remains available for comparison, but the selected backend uses branch-free repair and leaves register allocation to the driver.

The compiler is linked into `ShaderCorrectionGuards`' native adapter. `EVE.CloudShaderPacking` controls compilation independently of the existing guard flag and defaults to false. Windows x64, D3D11 and feature level 11.0 are required. The adapter recognizes candidate instructions rather than assembly MVIDs or shader identities. Unsupported programs and failed D3D shader creation use the original program. Both the original and guarded shader creation paths pass through the same adapter. Creation returns the original shader object; substitution happens when binding it. Variants belong to the source shader through D3D private data, and the render cache keeps only variant state. This avoids retaining every source object across reloads. Bytecode is cached by input SHA-256 within the process; no upstream shader binaries are distributed.

Build the inspector with `Build-Inspector.ps1`. Build the optimizer and its ten tests with `Build-Optimizer.ps1 -OutputDirectory <path> -Rustc <compiler>`. Build the native adapter with `../ShaderCorrectionGuards/Build-Native.ps1`. `tests/CloudPackingTests.cpp` checks actual D3D shader creation, guard composition, variant switching, source lifetime and the disabled path, using local input files supplied as arguments.

Local evidence on RTX 4060: 3,165 extracted programs passed frontend round-trip validation; the recognizer accepted 1,632 `Scatterer-EVE/RaymarchCloud` variants from those bundles. The GPU conversion oracle matched all half inputs. Two captured flight states passed strict comparisons of 49 and 71 render outputs, including final color, with zero changed bytes. Ten optimizer tests include 1,024 generated masked programs, loop/branch preservation and empty-branch removal. The native adapter accepted 18 input shaders, preserved both existing guards and passed repeated source release checks without growing the live program count. Full upstream programs and captures remain in private diagnostic artifacts. These checks do not establish parity for untested scenes, mod versions or GPU drivers, and replay event durations are not live FPS.

The final same-process comparison used five samples per variant in frozen middle/post-fuel scenes after warming both paths. Post-fuel rendering increased from 25.77 to 27.12 FPS; the middle scene showed no meaningful change. Physics was frozen for this comparison. A separate short reload series had a large settling trend and is excluded from acceptance; a historical full-flight FPS difference is not treated as causal evidence. Native D3D timestamps confirmed the earlier order of GPU draw durations, so per-event serialization was ruled out as the explanation for the apparent regression. The 12/16 ms GPU targets remain unmet.

## Paired cloud maps

`EVE.CloudMapPacking` independently controls the Rust BC4-to-BC5 path. Compatible fresh configurations enable it; existing configs keep missing keys disabled. It preserves the half converter and correction guards. The transformer proves that two explicit-LOD samples use unchanged coordinates and LOD in the same loop iteration, then reconstructs their original single-channel return values from one two-channel fetch. Unsupported programs retain their previous shader.

The native adapter captures compressed bytes during texture creation, full uploads, or staging copies. It never reads a GPU texture back during rendering. A background worker interleaves existing blocks without recompression and creates an immutable paired texture on a multithread-capable D3D11 device. Rendering uses the previous path until that texture is ready. The draw path does not compile shaders, pack blocks, upload textures, or wait for the worker.

Only matching single-mip BC4 UNORM views with identical ordinary samplers and no U/V border addressing are substituted. Texture writes invalidate the pair; textures changing after preparation remain on the original path. Identical full uploads/copies retain the existing pair. CPU and GPU limits are derived from available/installed memory and the adapter's video-memory budget. Source retention leaves headroom for packing. A full cache rejects new pairs rather than repeatedly evicting and rebuilding them every frame. GPU cache entries are cleared on scene transitions; source bytes belong to texture lifetimes, and application shutdown cancels and joins the worker and releases payloads.

`CloudMapCacheTests.cpp` checks real D3D11 image-byte parity and actual substituted draws, repeated identical uploads, changed input fallback, staging Map/Unmap/copy, partial writes, memory rejection, scene clearing and shutdown. The production Rust transform reproduces all seven previously replay-tested bytecodes and rejects the other four captured variants. These checks do not replace a new in-game FPS measurement. Nsight Perf SDK is a profiling tool, not a runtime dependency.
